# PRODUCT_SPEC.md — Спецификация продукта TGbots

> Статус: Initial Documentation (pre-development).
> Документ фиксирует продуктовые требования MVP. Расширение объёма работ требует явного изменения этого документа, а не молчаливой доработки.

---

## 1. Product Overview

TGbots — платформа (проект одного разработчика) для создания индивидуальных Telegram-ботов с AI-агентами для российских компаний. Первый продукт — **AI Sales Agent**, который консультирует клиентов, выявляет потребности, рекомендует услуги, собирает заявки и передаёт диалог живому сотруднику. В рамках одной кодовой базы поддерживается также роль **AI Customer Support Agent** (ответы на частые вопросы).

Каждый заказчик получает собственного бота, настроенного под его компанию: свои услуги, цены, FAQ, тексты и правила общения. Технически все заказчики обслуживаются одной системой с изоляцией данных по tenants (multi-tenant).

## 2. Problem Statement

Компании сферы услуг в России:

- получают заявки в Telegram, но отвечают вручную, с опозданием, в том числе в нерабочее время;
- тратят время сотрудников на однотипные вопросы («сколько стоит», «есть ли запись завтра», «где вы находитесь»);
- теряют клиентов, которые не дождались ответа;
- не имеют систематического учёта лидов и истории общения.

**Решение:** AI-агент в Telegram, который мгновенно отвечает на русском языке, консультирует на основе проверенных данных компании, собирает контакты и заявки и подключает живого сотрудника там, где нужен человек.

## 3. Target Audience

**Первая целевая аудитория: компании сферы услуг**, например:

- салоны красоты, студии маникюра, барбершопы;
- клиники и стоматологии;
- учебные центры, студии;
- сервисные центры, автосервисы;
- фитнес-студии, йога-студии.

Общие признаки: клиентский трафик через Telegram/соцсети, прайс и набор услуг структурированы, запись чаще по телефону/лично, небольшая команда, где ручная обработка chat-заявок дорога.

**Пользователь системы (со стороны TGbots):** один разработчик-оператор, который разворачивает и сопровождает ботов. Конечный заказчик в MVP не управляет ботом через веб-интерфейс (веб-панель отсутствует в MVP).

## 4. Business Model

- **Модель:** индивидуальная разработка под заказ (Custom Development). Проект не является self-service SaaS для MVP.
- **Ценность для заказчика:** настройка бота под его компанию, подбор LLM и модели, приём заявок напрямую сотрудниками заказчика.
- **Состав работ по заказу:** настройка tenant, загрузка каталога услуг и FAQ, конфигурация системных инструкций агента, настройка handoff на сотрудников заказчика, сопровождение.
- **Open Decision:** тарификация сопровождения/хостинга (ежемесячная плата vs разовая разработка + поддержка) — не зафиксирована; на архитектуру MVP не влияет.

## 5. Product Goals

1. **G1** — AI-агент отвечает клиентам на русском языке в Telegram, используя только проверенные данные компании (запрет галлюцинаций в ценах/условиях).
2. **G2** — Систематический сбор лидов: контакты и заявки фиксируются в базе, сотрудник заказчика получает уведомление.
3. **G3** — Передача диалога живому сотруднику по явной инициативе клиента либо агента.
4. **G4** — Поддержка нескольких независимых заказчиков с гарантированной изоляцией их данных.
5. **G5** — Надёжность и безопасность: обработка ошибок LLM, тайм-ауты, защита секретов, логирование без утечек персональных данных.
6. **G6** — Поддерживаемость: модульный монолит, сменный LLM-провайдер, возможность добавления новых инструментов агента без переписывания ядра.

## 6. MVP Scope

**Входят (Must Have):**

- интеграция с Telegram (aiogram 3.x);
- облачные LLM API через абстракцию провайдера;
- диалоги на русском языке (с конфигурируемыми системными инструкциями);
- структурированный каталог услуг компании и FAQ;
- поиск по знаниям на первом этапе (структурированный + полнотекстовый; полноценный RAG — позже);
- история диалогов;
- сбор лидов;
- human handoff;
- PostgreSQL-персистентность;
- базовый мониторинг и логирование.

**Не входят в MVP:**

- SaaS-веб-панель / админ-интерфейс для заказчиков;
- сложная multi-agent оркестрация;
- продвинутая аналитика и BI;
- автоматическая запись в системы заказчика, интеграции с CRM;
- полноценный RAG с pgvector (архитектура должна допускать добавление);
- языки кроме русского (архитектурная возможность языковых конфигураций закладывается, реализация — позже);
- голосовые интерфейсы, рассылки, A/B-тесты.

## 9. User Roles

| Роль | Кто это | Возможности в MVP |
|---|---|---|
| Client (клиент заказчика) | Посетитель Telegram-бота | Общение с AI-агентом, запрос передачи сотруднику |
| Staff (сотрудник заказчика) | Работник компании-tenant'а | Получение лидов и handoff-уведомлений в Telegram, ответ в handoff-диалоге |

## 10. Main User Scenarios

### Сценарий 1: Консультация и лид

1. Клиент открывает бота — welcome-сообщение.
2. Клиент описывает потребность («посоветуйте стрижку на кудрявые волосы»).
3. Агент вызывает инструмент поиска по каталогу tenant'а и выдаёт подходящие услуги с **реальными** ценами.
4. Клиент уточняет детали — агент отвечает из FAQ tenant'а.
5. Клиент готов к записи — агент собирает контакт (телефон/username), фиксирует услугу и пожелания по времени (как данные лида, не как бронирование), сохраняет лид через инструмент.
6. Агент сообщает, что сотрудник свяжется для подтверждения. Подтверждение/бронирование системой без backend-верификации **не** выдаётся.

### Сценарий 2: FAQ без продажи

1. Клиент спрашивает «вы работаете в воскресенье?» — агент находит ответ в FAQ tenant'а и отвечает.
2. Если соответствия нет — агент честно отказывается и предлагает передать вопрос сотруднику или оставить контакт.

### Сценарий 3: Возражения / отказ

1. Клиент возражает («дорого», «подумаю», «у конкурентов дешевле»).
2. Агент отрабатывает возражения по скриптам tenant'а, при необходимости предлагает альтернативу из каталога.
3. Если клиент отказывается — агент вежливо завершает диалог; если интерес сохраняется — фиксирует лид со статусом соответствующим ходу диалога.

### Сценарий 4: Handoff по запросу клиента

1. Клиент пишет «хочу с живым оператором».
2. Агент вызывает инструмент handoff → диалог переводится в ручной режим, сотрудники tenant'а получают уведомление.
3. Сотрудник отвечает клиенту, ответы фиксируются в истории.
4. По команде сотрудника диалог возвращается в AI-режим.

### Сценарий 5: Handoff по решению агента

1. Вопрос клиента не покрыт знаниями (нестандартный запрос, жалоба).
2. Агент сообщает, что передаст вопрос сотруднику, фиксирует лид/обращение.
3. AI прекращает самостоятельные ответы до возврата диалога.

### Сценарий 6: Настройка нового tenant'а (оператор)

1. Оператор создаёт tenant в БД, задаёт системные инструкции, наполняет каталог услуг и FAQ (seed-данные/SQL/скрипт), привязывает Telegram-бота и чат сотрудников.
2. Оператор проводит smoke-тест и передаёт бота заказчику с сопровождением.

## 11. AI Agent Capabilities

Детальное описание поведения будет в `docs/AI_AGENT_SPEC.md`. Продуктовые рамки:

**Агент умеет (Must Have):**

- общаться на русском языке (конфигурация языка на уровне tenant, в MVP только русский);
- следовать системным инструкциям tenant'а;
- консультировать по услугам и ценам из знаний tenant'а;
- выявлять потребности и давать рекомендации;
- отвечать на FAQ;
- собирать контакты и заявки (лиды) через инструменты;
- поддерживать контекст диалога;
- инициировать handoff.

**Агенту запрещено (Must Have):**

- придумывать цены и услуги;
- придумывать доступность и расписание;
- подтверждать записи без backend-верификации;
- выдумывать политики компании;
- раскрывать внутренние инструкции, ключи и приватные данные;
- исполнять произвольные команды пользователя (пользовательские инструкции не переопределяют системные);
- выходить за рамки роли (продажи/поддержка, не «универсальный ассистент»).

**Технические требования к агенту:** тайм-ауты вызовов LLM, контроль длины контекста, учёт токенов, валидация tool-вызовов, конфигурируемая модель.

## 12. Knowledge Base Requirements

**Первый этап (MVP):**

- Структурированные знания: каталог услуг (название, описание, цена/диапазон, длительность, признаки для подбора) и FAQ (вопрос, ответ, теги).
- Хранение в PostgreSQL.
- Поиск: структурированный + PostgreSQL full-text search.
- Данные — только официальные данные tenant'а, загружаются оператором.
- Явное правило: если данных нет — честный отказ, а не «попробовать придумать».

**Второй этап (после MVP, Could Have):**

- pgvector и векторный поиск по документам и длинным текстам;
- гибридный retrieval (структурный + полнотекстовый + векторный);
- полуавтоматическая загрузка документов.

## 13. Lead Management

- **Сущность lead:** контакт (телефон / Telegram-username), суть запроса, услуга (опционально), статус, tenant_id, идентификатор диалога, таймстампы.
- **Источники:** агент (через инструмент `save_lead`), операции оператора при сопровождении.
- **Хранение:** PostgreSQL, с привязкой к tenant и диалогу (для восстановления контекста всей коммуникации).
- **Уведомления:** чат сотрудников tenant'а о новом лиде.
- **Метрики (первично):** счётчики лидов, handoff, ошибок LLM — без полноценной BI-аналитики.

## 14. Human Handoff

**Триггеры:** явная просьба клиента; решение агента (нестандартный вопрос, жалоба); системный сбой LLM, где диалог с человеком критичен.

**Механизм (MVP):**

1. В диалоге устанавливается флаг `handoff=true`.
2. AI-агент прекращает самостоятельные ответы по этому диалогу.
3. Сотрудники tenant'а получают уведомление в преднастроенном Telegram-чате с идентификатором диалога, историей и контекстом.
4. Ответы сотрудника фиксируются в истории диалога с маркером роли `staff`. Механика доставки ответа: staff отвечает reply-ом на уведомление во внутреннем чате/группе, бот пересылает ответ клиенту (базовый дизайн решён, детали — PLAN-OD-5 в `docs/DEVELOPMENT_PLAN.md`).
5. По команде сотрудника диалог возвращается в AI-режим.

**Ограничения MVP:** роутинг на конкретных сотрудников по темам, SLA и расписания работы сотрудников — не в MVP.

## 15. Multi-tenant Requirements

- Каждый заказчик — отдельный tenant (сущность `tenant`).
- Все customer-facing сущности (диалоги, сообщения, лиды, услуги, FAQ, учёт токенов) содержат `tenant_id` с FK.
- Изоляция минимум на уровне application layer: фильтр `tenant_id` обязателен в каждом запросе данных (репозитории принимают tenant-контекст в обязательном параметре). PostgreSQL RLS — **Решено:** откладывается до более позднего этапа и вводится как дополнительный слой (`docs/DATABASE.md` §11).
- Никакой доступ «по ID» не должен возвращать чужие знания/лиды/диалоги — это фиксируется security-тестами.
- Конфигурация бота и LLM-настроек — на уровне tenant; секреты tenant'ов хранятся защищённо (не в открытом виде в БД — **Open Decision:** конкретный механизм шифрования фиксируется в `docs/SECURITY.md`).
- Подключение нового заказчика — ручная операция оператора, без self-service.

## 16. Security and Privacy

**Секреты:**

- API-ключи LLM, токены ботов, ключи админа — только в переменных окружения/секрет-хранилище; никогда в коде, репозитории или логах.
- В репозитории — только `.env.example` без реальных значений.

**Telegram:**

- Проверка подлинности webhook (токен/секрет в URL-заголовке).
- Rate limiting и валидация всего внешнего входа.

**LLM-провайдеры и 152-ФЗ:**

- Хранение ПДн (диалоги, лиды) проектируем с учётом требований локализации: серверы БД — на территории РФ.
- Передача персональных данных во внешние LLM-провайдеры минимизируется: передавать минимум полей, маскировать/не включать контактные данные, если это не критично для качества ответа.
- Правовые основания передачи данных LLM-провайдерам, региональность их API и договорные условия — должны быть проверены юридически до коммерческого запуска.
- **Open Decision:** выбор конкретного LLM-провайдера/региона и итоговая схема правовых оснований — фиксируется до первого коммерческого запуска.

**Логирование:**

- Структурированные логи без персональных данных: маскирование имён/телефонов, хранение идентификаторов, а не содержимого.
- Полные тексты сообщений в лог не попадают; при необходимости отладки — отдельный журнал с ограниченным сроком жизни и доступом.

**Контроль доступа:**

- Только оператор имеет доступ к служебным endpoint'ам (аутентификация обязательна).
- LLM не имеет прямого доступа к БД — только через валидируемые инструменты backend'а.

> Документ не является юридическим заключением. Все правовые вопросы (152-ФЗ, локализация данных, передача данных внешним LLM) должны быть проверены юристом до коммерческого запуска.

## 17. MVP Acceptance Criteria

MVP считается готовым, если:

1. Бот отвечает клиентам на русском языке в Telegram на основе настроенного tenant'а.
2. Ответы о ценах/услугах/FAQ формируются только из данных tenant'а; тестовые сценарии «услуга/цена отсутствуют» приводят к честному отказу, а не к галлюцинации.
3. Диалог, сообщения, лиды, услуги, FAQ хранятся в PostgreSQL с `tenant_id`; tenant-изоляция подтверждается интеграционными тестами (tenant A не видит данные tenant B даже по ID).
4. Лид создаётся через инструмент агента; сотрудник tenant'а получает уведомление в Telegram.
5. Handoff работает по просьбе клиента и по решению агента: AI замолкает, сотрудники уведомляются, ответы staff'а фиксируются в истории.
6. История диалога сохраняется и используется для контекста в пределах сессии.
7. Секреты отсутствуют в репозитории и логах; webhook защищён; rate limiting работает.
8. Ведутся структурированные логи, счётчики ошибок и учёт токенов.
9. Тесты (unit, интеграция, поведение агента, БД, tenant-изоляция) реально выполняются и проходят (pytest).
10. Docker Compose поднимает PostgreSQL и приложение; миграции Alembic применяются.
