# DEVELOPMENT_PLAN.md — План разработки MVP TGbots

> Статус: Initial Documentation (pre-development). План описывает последовательность работ; точные сроки не установлены, пока не оценён объём реализации (см. §3).
> Согласован с `docs/PRODUCT_SPEC.md` (§6, §17), `docs/ARCHITECTURE.md` (§5–19) и `docs/DATABASE.md`.

---

## 1. Принципы плана

1. **Малые итерации.** Каждый этап разбит на нумерованные шаги, каждый шаг — самостоятельная задача, которую AI-кодер выполняет за одну итерацию и которую можно проверить отдельным прогоном тестов.
2. **Независимая проверяемость.** Этапы, не имеющие общих зависимостей, отмечены как независимо проверяемые; между ними можно ставить контрольные точки.
3. **Тесты — часть этапа.** Этап закрыт только когда его тесты фактически запущены и прошли (AGENTS.md §10, §15).
4. **Без преждевременной сложности.** Redis, микросервисы, веб-панель и multi-agent оркестрация в план не включены (AGENTS.md §14).

## 2. Этапы и зависимости

| Этап | Название | Зависит от | Можно проверять независимо? |
|---|---|---|---|
| 1 | Project Foundation | — | Да, полностью |
| 2 | Database Layer | 1 | Да (тесты против тестовой БД) |
| 3 | Telegram Integration | 2 | Да (приём/сохранение/эхо-ответ) |
| 4 | LLM Integration | 2 | Да — независимо от Этапа 3; Этапы 3 и 4 можно вести параллельно |

| 8 | Testing and Deployment | все предыдущие | Системная проверка MVP (§17 PRODUCT_SPEC) |

## 3. О сроках

Сроки этапов не фиксируются без оценки объёма. Оценка будет возможна после Этапа 1 (по скорости реальных итераций каркаса). План — это последовательность и критерии, а не календарь.

## Этап 1. Project Foundation

**Цель.** Работающий «пустой» монолит: приложение стартует, `/health` отвечает, тесты и CI настроены, secrets-политика закреплена.

**Задачи (итерации):**

1. Структура репозитория по `ARCHITECTURE.md` §5: `src/` с пустыми пакетами модулей; `pyproject.toml` с фиксированными зависимостями (FastAPI, aiogram, Pydantic 2, SQLAlchemy 2, Alembic, pytest) — пока только объявления, без функций кода.
2. Конфигурация: `src/config/` на pydantic-settings; чтение env; `.env.example` (без реальных секретов); `.gitignore` (безопасные исключения).
3. Заглушки-интерфейсы: пустые модули `agent_core/`, `llm_providers/`, `tools/`, `knowledge/`, ... — только пакеты и докстринги-назначения, без кода логики.
4. FastAPI-каркас: `src/main.py`, `src/api/health.py` (`/health`), запуск приложения.
5. Настройка структурированного логирования (`src/monitoring/logging.py`) с фильтром секретов (контроль источников — §12).
6. Docker Compose: сервисы `app` и `postgres` (версия PostgreSQL — 16); переменные окружения.
7. Проверка качества: ruff/mypy/pytest; их автоматический запуск (CI или pre-commit).

**Появляются файлы:** `src/main.py`, `src/config/*`, `src/api/health.py`, `src/monitoring/*`, `docker-compose.yml`, `pyproject.toml`, `.env.example`, базовые `tests/`.

**Зависимости:** нет.

**Критерии завершения:**

- `docker compose up` поднимает `app` + `postgres`; app стартует без ошибок.
- `GET /health` возвращает 200 (без проверки БД; DB-check добавляется на Этапе 2).
- Логирование выводит структурированные записи (JSON).
- pytest, ruff, mypy работают (не обязательно с высоким покрытием — пока нет логики).
- Никакие секреты не в репозитории (sample-проверка).

**Тесты:** unit-тесты конфигурации (валидация env, обработка отсутствующих переменных), тест `/health` (FastAPI TestClient), smoke-тест запуска.

## Этап 2. Database Layer

**Цель.** Полная схема из `docs/DATABASE.md` + механизм tenant-контекста + репозитории; миграции Alembic применяются.

**Задачи:**

1. `alembic init`, каталог `migrations/`, naming-convention SQLAlchemy (см. DATABASE.md §13).
2. ENUM-типы + первая миграция: `tenants` → tenant-таблицы (порядок FK: DATABASE.md §13).
3. Async-движок и сессии: `src/db/engine.py`, `src/db/session.py` (POSTGRES_DSN из env).
4. Модели SQLAlchemy 2 (декларативные, с `tenant_id`) в `src/db/models/`.
5. `TenantContext` и базовый `TenantRepository`: явная передача `tenant_id`, генерация UUID, `updated_at`.
6. Специализированные репозитории: tenants, bots, agents, services, customers, conversations, messages, faqs, leads, handoffs, token_usage (bookings и knowledge_documents — репозитории добавляются позже, при включении соответствующих модулей: см. Этапы 6 и 7).
7. `/health` расширяется DB-check (недоступность БД — 503).
8. Seed-скрипт/фикстуры для тестовых данных (тестовый tenant) — вне alembic history.

**Появляются файлы:** `migrations/*`, `src/db/{engine,session,base}.py`, `src/db/models/*.py`, `src/db/repositories/*.py`, тест-фикстуры.

**Зависимости:** Этап 1.

**Критерии завершения:**

- `alembic upgrade head` создаёт всю схему; `downgrade` корректно откатывает.
- Индексы/уникальные/частичные ограничения соответствуют `DATABASE.md` (проверяются SQL-инспекцией в тестах).
- `bots` не хранит открытые токены (колонка отсутствует по схеме).
- Частичная уникальность: customer по (tenant_id, telegram_user_id); один активный lead на диалог; один активный handoff.

**Тесты:**

- Database-тесты (с тестовой PostgreSQL — тестовым docker compose сервисом): миграции up/down, модельные инварианты (CHECK/уникальность), каскад `messages → conversations`.
- Tenant-isolation-тесты (первая партия): попытки чтения кросс-tenant — только пусто/ошибка.

## Этап 3. Telegram Integration

**Цель.** Приём сообщений клиентов от реального тестового бота, сохранение в БД, эхо-ответ (контур «вход → выход» без LLM/агента).

**Задачи:**

1. `src/telegram_adapter/`: Dispatcher aiogram 3, регистрация middleware для tenant-разрешения (по токен-фингерпринт бота из `bots`).
2. Определение tenant: для polling — по токену; для webhook — платформа отличает бота через `secret_token`/URI.
3. Нормализация Update → внутренние message-модели (Pydantic).
4. Webhook-эндпоинт в `src/api/`: проверка секрета HTTPS/заголовков, rate limiting per-user (простой in-memory/DB-счётчик).
5. Use case «приём сообщения» (`src/application/`): upsert customer, get/create conversation, insert message (идемпотентно по `telegram_message_id`).
6. Эхо-ответ: adapter отправляет обратно текст с префиксом (временная заглушка — заменяется на Agent Core в Этапе 5).
7. Обработка `/start` (welcome_message из `agents` тенанта) и `/help`; отказ на media (FR-1.4).
8. Отправка уведомлений: отдельный класс `Notifier` для сообщений в чаты сотрудников (полный набор — Этап 7).

**Появляются файлы:** `src/telegram_adapter/*` (dispatcher, middleware, routers, keyboards), `src/api/webhook.py`, `src/application/*`, `src/notification/notifier.py`, соответствующие `tests/`.

**Зависимости:** Этап 2 (персистентность + `bots`).

**Критерии завершения:**

- Реальному боту можно написать — сообщение появится в `messages`, эхо ответит.
- Повторный webhook (повторная доставка Telegram) не создаёт дубликатов.
- Чужой webhook-токен отклоняется.
- Флуд ограничивается rate limiter'ом (фиксируются лимиты).

**Тесты:** unit-тесты нормализации Update; интеграционные тесты use case «приём сообщения» (в т.ч. идемпотентность); тесты webhook-защиты; тесты rate limiter. При наличии сетевого тестового бота — ручной smoke.

## Этап 4. LLM Integration

**Цель.** Единый LLM-провайдер интерфейс + одна реализация OpenAI-compatible (основной провайдер MVP — см. §6 «Принятые решения»); тайм-ауты, ретраи, учёт токенов.

**Задачи:**

1. `src/llm_providers/base.py`: интерфейс `complete(messages, tools, model, ...) -> LlmResponse` + нейтральные схемы (ChatMessage, ToolSpec, ToolCall, LlmResponse, Usage).
2. Реализация `openai_like.py`: вызовы, тайм-аут (по умолчанию ~30 с), ограниченный retry с backoff, конвертация ошибок в доменные исключения (LLMTimeout, LLMUnavailable и т. д.).
3. `factory.py`: выбор провайдера/модели — платформенный дефолт из env, override из `agents.model`.
4. Учёт токенов: запись `token_usage` (асинхронная, не блокирует диалог; см. DATABASE.md §7 п. 6).
5. Fallback-семантика: доменные ошибки, которые Agent Core (Этап 5) превращает во вежливое сообщение.

**Появляются файлы:** `src/llm_providers/{base,schemas,openai_like,factory,exceptions}.py`, `tests/llm_providers/*`.

**Зависимости:** Этап 2 (конфигурация tenant). От Этапа 3 не зависит — они параллелятся.

**Критерии завершения:**

- Реальный вызов выбранного облачного LLM показывает ответ и `Usage` в `token_usage`.
- Тайм-аут и ошибки сети возвращают доменные исключения (без «сырых» HTTP-ошибок).
- Выбор модели per-tenant работает (override > платформенный дефолт).

**Тесты:** unit-тесты с fake-провайдером (структуры сообщений, tool-спецификации); тесты тайм-аута/ретраев (фейковый транспорт); тест учёта токенов (DB-интеграция). Манипулировать реальным LLM API — только в smoke-тесте, не в автоматическом прогоне.

## Этап 5. Agent Core

**Цель.** Полный контур диалога: Agent Core собирает контекст, ведёт автомат состояний, вызывает LLM и выполняет tool-calls, валидирует ответ. Работает с заглушками tools (Этап 6 реализует настоящие).

**Задачи:**

1. Автомат состояний диалога (состояния `conversation_state`); правила переходов; сохранение state в `conversations`.
2. Context Builder: окно истории по `max_context_messages` + `context_summary` (сжатые факты).
3. Tool-подсистема: `src/tools/registry.py` (реестр по имени, whitelist из `agents.allowed_tools`), Pydantic-схемы входов/выходов, лимит tool-петель за ход (≤ 5).
4. Заглушки-инструменты для тестирования (fake `search_services`, `search_faq`, `save_lead`, `handoff_request`) — чётко очерченный контракт, реализации заменяются на Этапах 6–7.
5. Agent Loop: LLM-запрос → ответ или tool-call → исполнение → повторный запрос → финальный ответ.
6. Валидация ответа: длина, отсутствие артефактов/секретов; при провале — регенерация или fallback-сообщение.
7. Fallback-политика: LLMTimeout/LLMUnavailable → вежливое сообщение клиенту + лог/метрика.
8. Сквозной use case: Telegram-адаптер → Application Service → Agent Core → ответ (замещает эхо из Этапа 3).

**Позволяется:** пока без базы знаний — агент честно отвечает «уточню у менеджера» на фактические вопросы (когда tools пустые/не отдают данных).

**Появляются файлы:** `src/agent_core/{state_machine,context_builder,agent_loop,policies,response_validator}.py`, `src/tools/{registry,base,schemas}.py`, `src/application/process_message.py`, обновлённый `src/telegram_adapter/`.

**Зависимости:** Этапы 3 и 4.

**Критерии завершения:**

- Реальный диалог через тестового бота работает со стабильным AI-ответом.
- Tool-петля ограничена; неизвестные инструменты отклоняются.
- При недоступности LLM клиент получает fallback-сообщение, не пустоту.
- В `messages` фиксируются роли и tool-метаданные.

**Тесты (первая большая партия agent behavior):**

- «Агент не выдумывает цены/услуги» — golden-сценарии с fake-LLM (ответ строго из tool-результатов).
- «Пользователь не может вызвать запрещённый инструмент» (prompt injection проверка).
- Ограничение контекста; восстановление state после рестарта (состояние в БД).
- Интеграционный тест: входящие message → agent loop → ответ сохранён и отправлен.

## Этап 6. Knowledge Base

**Цель.** Реальные источники правды: каталог услуг + FAQ + полнотекстовый поиск; инструменты `search_services`/`search_faq` заменяют заглушки.

**Задачи:**

1. Репозитории `services`/`faqs` (агрегаты: полнотекстовый поиск через `search_tsv`, фильтры по статусу/тегам/`valid_until`).
2. Реализация retrieval за интерфейсом (готова к замене на pgvector-версию после MVP).
3. Инструменты `search_services(query, filters, top_k)` и `search_faq(query, top_k)` — Pydantic-схемы entry/exit, whitelist-filters, подача top-k результатов в контекст.
4. Seed-данные демо-каталога (для тестов и пилота).
5. `knowledge_documents` — репозиторий + скелет загрузки (не обязателен в MVP; достаточно схемы).
6. Ответы агента об услугах/ценах — теперь из реальных данных тенанта; «нет данных» — честный отказ (FR-3.3).

**Появляются файлы:** `src/knowledge/{retrieval,search}.py`, `src/tools/search_services.py`, `src/tools/search_faq.py`, seed-скрипты, `tests/knowledge/*`.

**Зависимости:** Этап 2 (схема), Этап 5 (реестр инструментов).

**Критерии завершения:**

- Поиск по услугам/FAQ возвращает релевантные результаты на русском языке.
- Агент больше не выдаёт «придуманные» цены (проверяется на фикс-данных: вопрос «сколько стоит X, которого нет» — отказ).
- Поиск строго в рамках тенанта.

**Тесты:** retrieval-тесты (релевантность на фикс-каталоге), тесты схем инструментов, tenant-isolation поиска, agent behavior на знаниях (ответы только из каталога).

## Этап 7. Leads and Human Handoff

**Цель.** Сбор лидов, уведомления сотрудников, human handoff через внутренний чат/группу; модуль booking — включаемый скелет.

**Задачи:**

1. Инструмент `save_lead`: сбор/проверка контакта, дедупликация, lifecycle статусов; уведомление сотрудникам после COMMIT (DATABASE.md §7 п. 2).
2. `Notifier`: сообщения в `handoffs.staff_chat_id` (чат/группа сотрудников), с идентификатором диалога и контекстом.
3. Инструмент `handoff_request`: триггеры (клиент/агент/ошибка); переключение `handoffs` + `conversations.handoff_active` одной транзакцией (DATABASE.md §7 п. 3).
4. Режим handoff: Agent Core НЕ отвечает LLM на сообщения диалога с флагом; входящие сохраняются.
5. Механика ответа сотрудника: staff отвечает reply-ом на уведомление в чате/группе — бот пересылает текст клиенту, ответ сохраняется с role='staff' (проектное решение; детали реализации — PLAN-OD-5).
6. Возврат в AI-режим: команда сотрудника в reply (детали — PLAN-OD-5).
7. Booking-модуль (скелет): `tenants.booking_enabled`-проверки, инструмент-заглушка, отсутствие backend-источника — инструмент не включается (условие OD-5/*booking*).
8. Сценарий 1–5 из PRODUCT_SPEC §10 — прогон вручную на тестовом боте.

**Появляются файлы:** `src/tools/{save_lead,handoff_request}.py`, `src/leads/*`, `src/handoff/*`, расширение `src/notification/`, `tests/leads/`, `tests/handoff/`.

**Зависимости:** Этапы 2, 3, 5 (и частично 6 для контекста).

**Критерии завершения:**

- Лид создаётся агентом в диалоге; сотрудник получает уведомление; повтор в том же диалоге — обновление, не дубликат.
- Handoff: агент замолкает, уведомление в чат, ответ staff виден клиенту и сохранён; возврат в AI работает.
- Сценарий передачи по системной ошибке (сбой LLM) — детерминирован.
- Booking: при disabled — инструменты не предлагаются агенту; при enabled — создаётся только `requested`.

**Тесты:** сквозные интеграционные сценарии (лид + уведомление с mock-Telegram), транзакционная целостность handoff (активность только на диалог), tenant-isolation лидов/handoffs, agent behavior тесты запретов («не подтверждать записи»).

## Этап 8. Testing and Deployment

**Цель.** Полный прогон всех категорий тестов, deploy-настройки, наблюдаемость, подготовка к пилотному заказчику.

**Задачи:**

1. Hardening-suite: полный pytest-прогон категорий unit / integration / agent behavior / database / security+tenant isolation (AGENTS.md §10), запуск всех категорий одной командой.
2. Аудит секретов: секреты не в коде/логах; webhook-токен не логируется; проверка маскирования персональных данных в логах (PRODUCT_SPEC §16).
3. Rate limiting/тайм-ауты/защита webhook — финальные проверки в прод-конфигурации (NFR-1, NFR-2).
4. Backup-процедуры (DATABASE.md §14): ручной restore-тест на staging; решение DB-OD-5.
5. Docker Compose на РФ-виртуалке/хосте; `alembic upgrade head` перед стартом; `/health` мониторинг.
6. Обновление документации: `README.md` (добавляются реальные команды запуска), `docs/SECURITY.md`, `docs/API.md`, `docs/AI_AGENT_SPEC.md`.
7. Приёмка MVP по `PRODUCT_SPEC` §17 (10 критериев) — финальная чеклист-приёмка.

**Появляются файлы:** `docs/SECURITY.md`, `docs/API.md`, `docs/AI_AGENT_SPEC.md`, обновление `README.md`, CI/deploy-скрипты, финальная версия тестов.

**Зависимости:** все предыдущие.

**Критерии завершения:** соответствие Definition of Done (AGENTS.md §15) и PRODUCT_SPEC §17 полностью.

**Тесты:** полный регресс + security suite + restore-тест. Ничего «не выполненного» не заявляется как пройденное.

## 4. Принятые решения (зафиксировано по заданию)

| Решение | Где реализуется |
|---|---|
| Один основной LLM-провайдер в MVP (OpenAI-compatible); через `llm_providers/base.py` — подключение других | Этап 4 |
| Изоляция tenant-данных на уровне приложения — обязательна; RLS — позднее как доп. слой | Этап 2 (app), RLS — вне MVP |
| Handoff — через внутренний Telegram-чат или группу сотрудников | Этап 7 (схема `handoffs.staff_chat_id` в DATABASE.md §4.11) |
| Персональные данные минимизируются перед отправкой во внешний LLM | Этап 4/5 (контекст-билдер + правила в `docs/SECURITY.md`) |
| Booking — модульный: включается только конкретно для тенанта, при backend-проверяемом источнике | Этап 7 (скелет), таблица `bookings` |
| Секреты платформы — вне исходного кода (env/секрет-хранилище) | Этапы 1–2 |
