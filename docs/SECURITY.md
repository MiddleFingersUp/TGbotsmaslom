# SECURITY.md — Требования безопасности TGbots

## 1. Security Overview

Система обрабатывает три категории чувствительных данных:

| Категория | Примеры | Зона защиты |
|---|---|---|
| Секреты доступа | бот-токены, ключи LLM, DSN, webhook-секреты, админ-токен | env / шифрование / секрет-хранилище; никогда в Git и логах |
| Персональные данные клиентов | телефон, username, имя, тексты сообщений, контакты лидов | PostgreSQL (в РФ), минимизация, сроки хранения, удаление |
| Бизнес-данные тенанта | каталог услуг, FAQ, диалоги, лиды, конфигурация агента | tenant-изоляция (уровень приложения + RLS позднее) |

Три линии обороны:

1. **Периметр:** проверка подлинности webhook, HTTPS, rate limiting, валидация входа.
2. **Идентичность и доступ:** привязка запросов к тенанту, явный `tenant_id` в каждом запросе, whitelisting инструментов агента.
3. **Данные:** шифрование секретов, минимизация персональных данных перед LLM, retention и удаление.

Ответственный — один оператор проекта; процесс рассчитан на одного человека (см. §17).

## 2. Security Principles

1. **Наименьшие привилегии.** Каждый компонент имеет доступ только к тому, что ему нужно: LLM — не имеет доступа к БД; агент — только к whitelisted-инструментам; приложение к БД — под непривилегированной ролью.
2. **Defense in depth.** Изоляция тенантов реализуется как минимум на уровне приложения; RLS — второй слой, добавляемый позднее.
3. **Backend владеет правдой.** Никакое бизнес-решение не принимается на основании текста из LLM; LLM — генератор текста, а не исполнитель.
4. **Fail closed.** При сбое проверки (tenant-фильтра, секрета webhook, схемы инструмента) операция запрещается, а не «пропускается».
5. **Минимизация данных.** Собираем и передаём только те данные, которые нужны для функции; персональные данные не попадают в логи и не пересылаются во внешний LLM без необходимости.
6. **Секреты не пересекают границу.** Секреты не хранятся в Git, не попадают в логи, в ответы клиенту и в промпты.
7. **Не доверять внешнему контенту.** Тексты пользователей и документы базы знаний — данные, а не инструкции (см. §12).
8. **Валидация всего входа.** Любые внешние данные (Telegram updates, аргументы инструментов, админ-API) проходят через Pydantic-схемы.
9. **Возможность отзыва.** Любой выданный доступ (бот-токен, ключ, webhook) должен отключаться без пересборки кода — через конфигурацию и БД.

## 3. Secrets Management

**Классификация секретов:**

| Секрет | Класс | Хранение |
|---|---|---|
| API-ключ облачного LLM | платформенный | переменная окружения (единственный основной провайдер MVP); смена — без правки кода |
| DSN PostgreSQL | платформенный | env (compose-переменная) |
| Токен админ-API оператора | платформенный | env |
| Webhook-секрет платформы | платформенный | env |
| Токен бота тенанта | tenant-секрет | по схеме `bots.secret_source`: `env` / `cipher` (AES-256-GCM в БД) / `vault` (external store) |
| Webhook-секрет бота тенанта | tenant-секрет | по схеме `bots.webhook_secret_ciphertext` |

**Правила:**

1. Ничего секретного в репозитории; в Git только `.env.example` с пустыми плейсхолдерами. Предотвращение случайного коммита: `.gitignore` + сканер секретов в CI (Этап 8, §18).
2. Токен бота в открытом виде не хранится в PostgreSQL — колонка в схеме отсутствует принципиально; хранится только `token_fingerprint` (первые 16 hex-символов SHA-256) для защиты от повторного использования одного токена двумя тенантами (см. `docs/DATABASE.md` §4.2).
3. Бот-токены и ключи выдаются по минимально необходимому кругу; при потере (утечке ноутбука, случайной отправке в чат) — немедленная ротация: BotFather revoke, смена ключа LLM у провайдера, обновление секрета в хранилище.
4. В качестве fingerprint используется SHA-256 полного значения токена — по хэшу невозможно восстановить токен. Хэш хранится целиком; первые 16 hex-символов — человекочитаемый ярлык для сопоставления записей.
5. Логирование секретов технически исключено: фильтр на структурированном логировании (Этап 1) закрывает трассы с именами `token`, `secret`, `password`, `key` — значение заменяется на `[REDACTED]`.
6. Определение платформенных секретов — только через pydantic-settings; старт без required-секретов — ошибка конфигурации, а не «работа с дефолтом».

## 4. Encryption at Rest

**Приложение-уровень (tenant-секреты):**

- Алгоритм — authenticated encryption **AES-256-GCM** через библиотеку `cryptography` (AEAD: шифрование и аутентификация целостности в одной операции). Схема записи в БД: `key_version (int) || nonce (12 байт) || ciphertext || tag`.
- AAD (associated data) привязывает шифротекст к владельцу — `tenant_id` и `bot_id` — защита от «пересадки» шифротекста в другой тенант.
- Ключ шифрования **не хранится рядом с данными**: в PostgreSQL — только шифротекст; ключ — в env/внешнем хранилище (точный источник — SEC-OD-2, §19).
- Формат покрывает то, что уже спроектировано в схеме: `bots.token_ciphertext`, `bots.webhook_secret_ciphertext` (`docs/DATABASE.md` §4.2); длина полей рассчитывается с запасом на полный шифротекст + тег + префикс версии.

**База данных (персональные данные).** Тексты сообщений, контакты и лиды хранятся в PostgreSQL в открытой форме на уровне столбцов — целостность обеспечивается:

- дисковым шифрованием хостера / LUKS-шифрованием диска (выбор хостинга — SEC-OD-5, до Этапа 8);
- разграничением доступа (роли БД, §11), сетевой приватностью (БД не публикуется наружу);
- обязательной изоляцией тенантов (§6) и (позднее) RLS (`docs/DATABASE.md` §11);
- минимальным сроком хранения (§15).

**Бэкапы** — всегда шифруются (§16).

## 5. Encryption Key Rotation

Процедура ротации ключа шифрования tenant-секретов:

1. **Версионирование ключей.** Ключи хранятся как нумерованные версии (`kek/v1`, `kek/v2`, ...); каждая запись шифротекста содержит `key_version` — расшифровка выполняется ключом именно указанной версии.
2. **Ре-шифрование.** Фоновая процедура: чтение шифротекста ключом версии N → запись ключом версии N+1 (в одной транзакции на запись). Пока есть неполные записи, старый ключ не удаляется.
3. **Триггеры ротации:** по расписанию (ориентир — раз в 12 месяцев), при компрометации, при уходе человека с доступом к ключу.
4. **Ротация фактических секретов** (бот-токен, ключ LLM) — отдельная процедура от ротации ключа шифрования: новые значения замещают старые в секрет-хранилище; при ротации ключа шифрования значения секретов не меняются — перешифровываются.
5. **Критичность:** компрометация ключа версии N компрометирует только те шифротексты, которые написаны этой версией и не перешифрованы; компрометация невозможна без доступа к хосту/хранилищу ключа.

## 6. Tenant Isolation

Зафиксировано ранее (см. `docs/DATABASE.md` §9 и `docs/ARCHITECTURE.md` §15), здесь — снова в терминах безопасности:

1. **Уровень приложения — обязательный слой.** `tenant_id` передаётся явно с каждым запросом (аргумент репозитория); запрос к tenant-таблице без фильтра по `tenant_id` не существует в бизнес-коде; конфигурация LLM/ботов берётся только из текущего тенанта.
2. **RLS — второй слой, добавляемый позднее** (`docs/DATABASE.md` §11) — включается на работающем приложении без изменения бизнес-кода; требуется выделенная непривилегированная роль БД.
3. **Межтенантные утечки запрещены структурой данных:** уникальность идентичности клиента внутри тенанта (`customers: UNIQUE (tenant_id, telegram_user_id)`), уникальность бот-токена (`bots.token_fingerprint`), жёсткая привязка диалогов/лидов/handoff к тенанту через FK.
4. **Тесты — обязательная категория** (§18): сценарии «тенант A читает объект тенанта B по ID» и «селект без tenant-фильтра» должны завершаться отказом.
5. **Отдельно:** маршрутизация webhook по `secret_token` бота исключает подмену тенанта через подделку update'а; секрет бота никогда не выдаётся наружу (не возвращается в API, не логируется).

## 7. Personal Data Protection

**Классификация ПДн в системе:**

| Объект | Данные | Основание хранения |
|---|---|---|
| `customers` | username, имя, телефон, язык, ID Telegram | исполнение запроса клиента / интерес (уточняется юристом — SEC-OD-9) |
| `messages` | текст сообщений | история диалога (функционально необходима) |
| `leads` | контакты, суть запроса | законный интерес бизнес-процесса |
| `token_usage` | метаданные, без ПДн | статистика |

**Требования:**

1. **152-ФЗ (Россия) — обязательная рамка:** фиксация целей обработки; ограничение объёма; сроки хранения; локализация баз данных, содержащих ПДн граждан РФ, на серверах в РФ; права субъекта (уточнение, блокировка, удаление, отзыв согласия).
2. **Правовые основания обработки** — фиксируются юристом до пилота (SEC-OD-9): какие основания (согласие / исполнение запроса / законный интерес) применять к категориям данных.
3. **Локализация данных:** PostgreSQL и бэкапы — только на серверах в РФ (§16); передача данных внешнему LLM-провайдеру — предмет §8.
4. **Минимизация и маскирование:** телефон, username, имя не логируются; при отправке контекста в LLM — по возможности маскируются (§8); лид создаётся только с согласия клиента оставить контакт (PRODUCT_SPEC §10 сценарий 1).
5. **Права субъекта:** запрос «удалите мои данные» — операционная процедура: анонимизация customer'а и снапшотов в лидах (см. `docs/DATABASE.md` §10); детали — SEC-OD-3.
6. Документ **не является юридическим заключением**; коммерческий запуск — только после юридической проверки (см. §19 SEC-OD-9).

## 8. LLM Data Privacy

Конкретный LLM-провайдер **не выбран** (PLAN-OD-1 / SEC-OD-1); архитектура — один основной провайдер OpenAI-compatible за сменным интерфейсом (`docs/ARCHITECTURE.md` §8).

**Что уходит внешнему провайдеру (по умолчанию):**

- system prompt тенанта (правила бота — без ПДн);
- сжатый контекст диалога (включает тексты пользователя — неизбежно для качества ответа);
- top-k результаты инструментов (каталог услуг, FAQ) — бизнес-данные тенанта;
- tool-схемы (имена, параметры).

**Чего не уходит / маскируется:**

- API-ключи и любые секреты — никогда;
- конфигурация платформы (DSN, токен бота) — никогда;
- телефон и email при их наличии в истории — маскируются перед отправкой (**SEC-OD-4:** точные правила маскирования — что считать маскируемым и как выглядит маска — фиксируются до Этапа 5).

**Передача и трансграничность:**

- Локализация: БД в РФ (§7); облако LLM — как правило вне РФ → трансграничная передача ПДн, которая по 152-ФЗ требует проверки основания передачи и условий провайдера — **обязательная юридическая проверка до выбора провайдера (SEC-OD-1)**.
- Требования к провайдеру (чек-лист для выбора): регион/юрисдикция API, договорная отказ от обучения на пользовательских данных, нулевая/минимальная ретенция запросов, возможность DPA/дополнения к договору, SLA доступности и тарификация.
- Если провайдер/условия не проходят проверку — резервный вариант: локально размещаемая модель (open-weight на собственном VPS в РФ); в MVP не входит.

## 9. Telegram Security

1. **Webhook:** только HTTPS; проверка секретного заголовка (`X-Telegram-Bot-Api-Secret-Token` из секрета бота); подделка update'а — отклоняется; polling — только в dev-окружении.
2. **Идентичность тенанта:** входящие update'ы привязываются к `bots` по токену/секрету — чужой бот не может получить доступ к чужому тенанту.
3. **Rate limiting:** per-user лимит сообщений (защита от флуда и от «накрутки» расхода LLM); значение задаётся в конфигурации, а не в коде.
4. **Медиа:** в MVP не обрабатываются — вежливая просьба написать текст (FR-1.4); это также защита от скрытных векторов (файлы, ссылки на непроверенные источники).
5. **Не доверять содержимому update:** текст сообщения — данные (см. §12); chat-id/user-id используются только для маршрутизации.
6. **Чат сотрудников:** уведомления о лидах/handoff содержат персональные данные; доступ к чату должен быть ограничен сотрудниками тенанта (кто состоит в чате — ответственность заказчика; это фиксируется в договоре, не в коде); бот публикует в чат только необходимый минимум (см. PRODUCT_SPEC §14).

## 10. API Security

Состав API MVP (`docs/ARCHITECTURE.md` §6, §16):

| Endpoint | Доступ | Защита |
|---|---|---|
| `POST /telegram/webhook/{bot_id}` | Telegram | секретный заголовок бота; валидация Pydantic; rate limit |
| `GET /health` | публичный | без данных; 200/503 |
| внутренние endpoint'ы мониторинга/админ-API | только оператор | платформенный админ-токен из env; HTTP-заголовок; HTTPS-only |

Правила:

1. Ошибки наружу — не раскрывают stack trace, DSN, версии, секреты; наружу уходит доменный ID ошибки (в логах он же).
2. Валидация всего входа через Pydantic; размер тела запроса ограничивается (защита от «прокачки» промпта/DoS).
3. CORS — не открывается (нет браузерных клиентов в MVP).
4. Никаких экспериментальных/exp/debug endpoint'ов в прод-конфигурации.

## 11. Authentication and Authorization

| Роль | Способ аутентификации | Разрешения |
|---|---|---|
| Client | Telegram-идентичность, привязанная через бот-токен к тенанту | общение с агентом; действия — ТОЛЬКО через whitelisted-инструменты; админ-действия недоступны; передача к сотруднику — только через инструмент `handoff_request` |
| Staff (сотрудник тенанта) | состоит во внутреннем чате/группе тенанта (**SEC-OD-8:** вариант «явный список staff» с таблицей — рассматривается; сейчас — по факту доступу к чату) | получение уведомлений, ответ в handoff-диалоге, возврат в AI-режим; нет доступа к чужим тенантам |
| Operator (оператор) | админ-токен платформы из env | управление тенантами, секретами, мониторингом; единственная роль с доступом ко всем данным — доступ явно фиксируется и логируется |
| Системные роли БД | непривилегированная роль приложения, отдельная роль миграций | приложение — только DML; миграции — DDL; RLS-ready |

Правила: разграничение — наименьшие привилегии; никакой роли «всё в одном»; доступ оператора к персональным данным — только по необходимости; события оператора логируются.

## 12. Prompt Injection Protection

**Источники недоверенного контента:** сообщения клиента; тексты `knowledge_documents` (создаются оператором, но всё равно не инструкции); результаты внешних инструментов (будущее).

**Обязательные защиты (реализация — Этап 5):**

1. Разделение ролей в промпте: системные инструкции — это ТОЛЬКО то, что лежит в `agents.system_prompt`; пользовательский контекст не встроен в системную роль.
2. Контент пользователя и документов передаётся как данные (отдельные сообщения roles user/document с разделителями) — так, чтобы они не могли переопределять системные правила; прямых конкатенаций «инструкция + текст пользователя» не допускается.
3. Запрет «повышения привилегий» через текст: даже если LLM «согласится» позвать несанкционированный инструмент — реестр инструментов вернёт отказ, т.к. whitelist состояния диалога (`agents.allowed_tools` + state) проверяется **в коде**, а не в промпте.
4. Response Validator (ARCHITECTURE §7) проверяет финальный ответ на уход за рамки роли и появление запрещённых сущностей (секреты, системные промпты, дампы).
5. Агенту нельзя «отменить» handoff, подтвердить booking или выдать цену вне каталога — эти действия верифицируются кодом инструментов, а не инструкциями.
6. Фиксированная категория тестов в §18: golden-сценарии prompt injection (клиент, «документ», смесь) — проверка, что привилегии не растут.

## 13. AI Tool Execution Security

1. **Единственный исполнитель инструментов — backend.** LLM лишь заявляет намерение вызвать инструмент (имя + аргументы); реальный вызов делает код.
2. **Реестр и whitelist:** инструмент активен только если (а) зарегистрирован в Tool Registry, (б) включён в `agents.allowed_tools`, (в) доступен в текущем состоянии диалога (например, `save_lead` не вызывается после handoff).
3. **Валидация аргументов и результатов** — Pydantic-схемы входов и выходов; провал валидации — fail closed (структурированная ошибка агенту, повторная попытка лимитирована).
4. **Tenant-контекст:** каждый вызов инструмента выполняется в рамках тенанта, подтверждённого на этом update'е; инструмента «поиск по всем тенантам» не существует.
5. **Нет динамических инструментов:** LLM не может создать/зарегистрировать новый инструмент, изменить схему или «расширить» аргументы.
6. **Критические бизнес-операции:** подтверждение booking — только через `verified_by_backend` (CHECK в БД, `docs/DATABASE.md` §4.9); агент может создать только status='requested'.
7. **Аудит:** параметры вызовов и результаты фиксируются в `messages.meta` (без секретов и полного текста персональных данных, где возможно).
8. **Лимит tool-петель** за ход (≤ 5) — защита от зависших циклов и от расхода токенов.

## 14. Logging and Monitoring

1. **Структурированные JSON-логи** (Этап 1): поля события, tenant_id, conversation_id, модуль, уровень, error-код; **БЕЗ** текстов сообщений, телефонов, имен, usernames и секретов.
2. **Маскирование:** секреты всегда фильтруются (§3.5); тексты сообщений по умолчанию не логируются — только идентификаторы и счётчики.
3. **Метрики MVP:** счётчики входящих/ответов/ошибок LLM/ошибок инструментов/handoff; сумма токенов per tenant (записывается в БД — изолированно); stderr/stdout — в хост-лог.
4. **Оповещения:** пороги на частоту ошибок LLM/инструментов и недоступность БД (`/health`); канал — Telegram-уведомления оператору (минимальный вариант вместо полноценного observability-стека).
5. **В логах не содержатся:** токены ботов, ключи LLM, DSN, персональные данные. Проверка — тест-категория в §18.
6. **Retention of logs** — SEC-OD-7 (открыто): предложение — платформенные лог-каналы с историей 14–30 дней.

## 15. Data Retention and Deletion

База — `docs/DATABASE.md` §10; здесь — сводка в терминах безопасности и 152-ФЗ:

1. **Закрытые диалоги** — удаляются по истечении `retention_days` (per-tenant или платформенный дефолт; **DB-OD-1** — значение, предложение 180 дней).
2. **Статусы вместо удаления (soft delete):** услуги/FAQ/агенты/боты/документы — статус `archived`/`inactive`, физическое удаление — только при offboarding тенанта.
3. **Просьба субъекта «удалите мои данные»:** анонимизация `customers` (обнуление phone/username/first_name) и снапшотов в лидах; тексты сообщений — по правилам **SEC-OD-3** (решается до Этапа 3, согласуется с правовой проверкой).
4. **Offboarding тенанта:** архивация → отключение ботов → удаление токенов из хранилища → полное удаление данных по истечении срока отсрочки (30–90 дней, **DB-OD-3**); бэкапы, содержащие данные тенанта, удаляются в рамках обычной ротации бэкапов.
5. **Сроки хранения — обязательная часть рамки 152-ФЗ** (правовая проверка SEC-OD-9); никаких бессрочных данных без цели.
6. Факт удаления фиксируется (какое удаление, когда, кем) — минимальный аудит-след.

## 16. Backup Security

1. Бэкапы — только на серверах в РФ, шифруются (§4); содержат персональные данные → режим обращения «как продакшн-данные»: доступ только оператору, доступ логируется.
2. Композиция — `docs/DATABASE.md` §14: ежедневный full + непрерывный WAL, RPO ≤ 15 мин, RTO ≤ 2 ч, ротация 30 дней, тестирование восстановления не реже раза в месяц.
3. **Инструмент бэкапов (DB-OD-5 / SEC-OD-6):** управляемый PostgreSQL российского хостера с его встроенными бэкапами vs pgBackRest/wal-g на VPS — решается до Этапа 8.
4. Компрометация бэкапа = потенциальная утечка персональных данных всех тенантов: бэкапы никогда не размещаются в публичных bucket'ах/облаке; ключ дешифровки — не рядом с бэкапом.

## 17. Incident Response

Минимальный процесс (проект одного оператора):

1. **Обнаружение** — мониторинг (§14), сообщения клиентов, алерты хостера.
2. **Сдерживание (containment):** типовые действия заранее описаны и отрепетированы:
   - утечка секретов → ревокация (BotFather, панель LLM, смена админ-токена) + ротация ключа шифрования (§5);
   - обнаруженный prompt injection/аномалия → остановка бота (is_active=false) или handoff всех активных диалогов;
   - подозрение на межтенантную утечку → остановка приложения / перевод БД в readonly и фиксация состояния.
3. **Оценка:** какие данные, какие тенанты затронуты; сопоставление с обязательствами 152-ФЗ.
4. **Уведомления:** правовая обязанность информировать субъектов/регулятор — проверяется юристом как часть SEC-OD-9; к моменту запуска должен быть готов шаблон коммуникации с заказчиком (рамка договора).
5. **Восстановление:** возврат в рабочий поток с учётом причины; заметка-постмортем в репозитории (без секретов и персональных данных).
6. **Репетиция:** tabletop-сценарий «утёк бот-токен» и «утёк ключ LLM» — перед запуском (Этап 8).

## 18. Security Testing

Обязательная тестовая категория (AGENTS.md §10 — «Security and tenant isolation tests»), на Этапах 2, 5, 7, 8:

| Категория | Проверки |
|---|---|
| Tenant isolation | кросс-tenant чтение/запись по ID; SELECT без tenant-фильтра; подмена tenant через идентичность клиента; поиск знаний без фильтра |
| Secrets | сканер секретов в Git (CI); лог-фильтр (нет секретов в трассах); отсутствие plaintext-колонок в схеме; шифрование round-trip (AES-256-GCM + AAD + версионирование) |
| Webhook / Telegram | чужой secret-token; подделка update; дубликат webhook (идемпотентность); rate limiter |
| Prompt injection | инъекция в сообщении клиента, инъекция в «документе» базы знаний, попытка вызвать несанкционированный инструмент, попытка выдать цену вне каталога |
| Tool execution | валидация аргументов/результатов; whitelist по состоянию диалога; tenant-контекст; лимит петель; booking — только через backend-верификацию |
| API | админ-токен обязательный; ошибки не раскрывают внутренности; лимит тела запроса |
| Retention/deletion | анонимизация по запросу; expiry-джоб данных (тест на fixture-сроках) |
| Ops | restore-тест бэкапа (Этап 8); fail-closed при недоступности LLM (нет пустых или обрывочных ответов) |

Плюс: проверка pip-зависимостей на известные уязвимости — Should Have на Этапе 8. Минимальный ручной security-обзор перед пилотом — обязателен.
